# 飞书 Playbook 正向重编设计

## 目标

把现有飞书 Playbook 从“AI 生成的完整知识目录”重编成一份有明确判断、具体做法和真实工作感的个人实战手册。

核心表达原则是：全篇采用肯定、建设性、可执行的说法。文章直接告诉读者适合怎么做、什么条件下这样做、怎样验收结果，让内容读起来像一个实际搭过系统的人在交接经验。

## 编辑合同

- 模式：全文深改与结构重编。
- 体裁：面向个人开发者和小团队的公开实战手册。
- 声纹：直接、克制、有判断，优先使用具体动作、对象和结果。
- 表达：以肯定句为主，使用“适合”“推荐”“优先”“配合”“按照”“把……放在……”等表达。
- 保护项：事实、日期、数字、引用、链接、命令、接口、技术术语、代码和安全边界保持准确。
- 不新增：个人经历、未经验证的事实、虚构案例、虚构数据和夸张承诺。

## 主要改动

### 1. 重写首屏和总论

首屏直接说明这份手册能帮助读者搭建什么系统、从哪里开始、最终会得到什么结果。把抽象的“AI-First”“工作操作系统”等概念落到工作简报、会议行动、知识检索、内容发布和项目协作等具体场景。

### 2. 以工作结果组织章节

保留现有信息资产，但把章节主线调整为：

1. 飞书在个人工作系统中的位置；
2. 工具组合与选择顺序；
3. 场景筛选方法；
4. 个人工作流；
5. 开发者工作流；
6. 数据、知识和执行系统；
7. Skill 的设计与交付；
8. 参考项目与借鉴重点；
9. 稳定运行的方法；
10. 运营、治理和 30 天落地计划。

将“反模式”改成“稳定运行的设计准则”，把每条内容改写为正向动作，例如“为每个对象保留权威来源”“写入前准备候选记录”“为每个流程设置结束条件”。

### 3. 统一标题和段落节奏

标题优先使用“怎么做”“适合什么”“推荐配置”“验收标准”“设计准则”等词。每个场景尽量采用同一套可读结构：

1. 适用场景；
2. 目标结果；
3. 最小流程；
4. 推荐数据或权限配置；
5. 示例；
6. 验收指标。

删除只承担路标作用的重复总结、抽象拔高和同义循环；保留足以帮助读者执行的列表、表格、代码和引用。

### 4. 把否定式信息改成正向边界

技术边界和安全要求继续保留，但统一落成可执行规则：

- 将“飞书不适合承载高频原始数据”改为“高频原始数据放入本地数据库，飞书保留筛选后的状态和结果”；
- 将“不要自动写入正式知识库”改为“先生成候选内容，确认后写入正式知识库”；
- 将“避免权限过大”改为“按身份和动作拆分权限”；
- 将“反模式”章节改成“稳定运行的设计准则”。

不为了追求表面正向而删除配额、权限、错误恢复、人工确认等必要边界；这些内容用“推荐配置”和“上线检查”表达。

### 5. 同步交付物

正文真源为 `docs/index.md`。完成正文后运行现有 `pnpm sync:readme`，同步 `README.md`；重新构建会生成并更新站点产物及 `docs/public/llm.txt`。不手工编辑生成产物。

## 验证标准

- 全文标题和正文完成正向表达重构，旧的“反模式”命名与明显否定式包装被收口。
- 事实、数字、命令、链接、引用和代码仍可逐项对回原稿。
- `pnpm check` 通过。
- 线上 `https://chendahuang.com/playbook/feishu/` 返回 200，并包含新首屏与新章节标题。
- Git 工作区在提交前只包含本次改写相关变更。

## 发布顺序

1. 修改 `docs/index.md`；
2. 运行 `pnpm sync:readme`；
3. 运行 `pnpm check`；
4. 检查 diff 和 live build 关键字；
5. 提交并推送 `feishu-playbook`；
6. 运行 `pnpm deploy:quick`；
7. 用生产 URL 做 HTTP 与正文验证。
